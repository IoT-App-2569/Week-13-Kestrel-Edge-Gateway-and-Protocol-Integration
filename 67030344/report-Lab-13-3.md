# ใบงานการทดลองที่ 13.3
## 4. คำถามท้ายการทดลอง
1. เพราะเหตุใด SignalR จึงให้ประสบการณ์การใช้งาน (UX) บนหน้าเว็บที่ดีกว่าการใช้คำสั่ง JavaScript `setInterval()` เพื่อทำ HTTP GET Polling ซ้ำๆ ทุก 500 ms?

```text
**SignalR ใช้การเชื่อมต่อ WebSocket ที่เปิดค้างไว้ ให้ Server ผลักข้อมูลมาหน้าเว็บทันทีที่มีค่าใหม่ แทนการให้เบราว์เซอร์คอยถามซ้ำๆ ว่ามีข้อมูลใหม่หรือยัง**
 
- **ข้อมูลมาถึงทันที** เมื่อ `SerialBridgeWorker` ได้รับข้อมูลจากบอร์ด จะเรียก `SendAsync("ReceiveTelemetry", ...)` ส่งถึงหน้าเว็บในเสี้ยววินาที ส่วน Polling ทุก 500 ms อาจทำให้ข้อมูลล่าช้าได้ถึงเกือบ 500 ms และเมื่อจังหวะ Polling ไม่ตรงกับจังหวะที่บอร์ดส่ง ก็จะได้ค่าซ้ำหรือข้ามบางค่าไป ตัวเลขบนหน้าจอจึงกระตุก
- **ลดภาระเครือข่ายและ Server** ทุกคำขอ Polling มี HTTP Header ขนาดหลายร้อยไบต์ และถูกส่งทุก 500 ms แม้ไม่มีข้อมูลใหม่ หากเปิดหน้าเว็บ 10 แท็บ Server ต้องตอบ 20 คำขอต่อวินาที ส่วน WebSocket มี Overhead ต่อข้อความเพียงไม่กี่ไบต์ และ `Clients.All` ส่งข้อมูลชุดเดียวกระจายถึงทุกหน้าในครั้งเดียว
- **สื่อสารสองทางผ่านช่องทางเดียว** การเชื่อมต่อเดียวกันใช้ทั้งรับ Telemetry และส่งคำสั่ง `connection.invoke("ToggleLed", ...)` และเมื่อมีผู้กดสวิตช์ Server จะกระจาย `LedStateUpdated` ให้ทุกหน้าที่เปิดอยู่ ปุ่มของผู้ใช้ทุกคนจึงแสดงสถานะตรงกัน ซึ่ง Polling ทำได้ช้ากว่าและซับซ้อนกว่า
- **จัดการการเชื่อมต่ออัตโนมัติ** `withAutomaticReconnect()` เชื่อมต่อใหม่เองเมื่อเครือข่ายหลุด และ SignalR เลือกช่องทางสำรองให้เองหากเครือข่ายไม่รองรับ WebSocket เช่น Server-Sent Events หรือ Long Polling
```

2. การคำนวณและแสดงผล Protocol Convergence Metrics ส่งผลดีต่อการตรวจสอบสุขภาพของระบบเครือข่ายไอโอทีในระดับโรงงานอย่างไร?

```text
**ตัวนับของแต่ละโปรโตคอลบอกได้ว่าข้อมูลไหลผ่านแต่ละขั้นของระบบครบหรือไม่ จึงระบุได้ทันทีว่าปัญหาเกิดที่ขั้นใด โดยไม่ต้องไปตรวจอุปกรณ์ทีละจุด**
 
- **ระบุจุดที่ข้อมูลขาดหาย** ข้อมูลไหลเป็นลำดับ Serial → MQTT → SignalR หากตัวนับ Serial หยุดเพิ่ม แสดงว่าปัญหาอยู่ที่บอร์ด สาย USB หรือพอร์ต COM หาก Serial เพิ่มแต่ MQTT ไม่เพิ่ม ปัญหาอยู่ที่ Broker และหาก SignalR ไม่เพิ่ม ปัญหาอยู่ที่ฝั่งเว็บ
- **ตรวจจับความผิดปกติจากอัตราการไหล** ในสภาวะปกติบอร์ดส่งข้อมูลประมาณ 2 แพ็กเก็ตต่อวินาที หากอัตราลดลง อาจเป็นสัญญาณว่าอุปกรณ์ค้างหรือสายหลวม หากอัตราสูงผิดปกติ อาจเป็นอุปกรณ์ทำงานผิดพลาดหรือมีการส่งข้อมูลถล่มระบบ
- **ตรวจสอบความสมบูรณ์ของข้อมูล** ในระบบที่ทำงานถูกต้อง ตัวนับทั้งสามควรเพิ่มขึ้นในอัตราเดียวกัน หากตัวนับเริ่มห่างกัน แสดงว่ามีข้อมูลสูญหายระหว่างทาง ซึ่งสำคัญมากในโรงงานที่ข้อมูลใช้ควบคุมคุณภาพการผลิต
- **วางแผนขยายระบบ** สถิติปริมาณข้อความช่วยประเมินภาระของ Gateway ว่ารองรับอุปกรณ์เพิ่มได้อีกเท่าใด ก่อนจะถึงขีดจำกัดของเครื่อง
```
