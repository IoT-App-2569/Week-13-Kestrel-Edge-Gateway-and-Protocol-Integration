# ใบงานการทดลองที่ 13.2
## 4. คำถามท้ายการทดลอง
1. สถาปัตยกรรมแบบ Serial-to-MQTT Bridge นี้ช่วยให้อุปกรณ์รุ่นเก่า (Legacy Hardware) ที่ไม่มี Wi-Fi สามารถเข้าร่วมระบบนิเวศ IoT สมัยใหม่ได้อย่างไร?

```text
**Gateway ทำหน้าที่เป็นตัวแปลงโปรโตคอล (Protocol Translator) รับข้อมูลจากสาย Serial แล้วเผยแพร่เป็น MQTT และ REST แทนอุปกรณ์ อุปกรณ์จึงเข้าสู่ระบบเครือข่ายได้โดยไม่ต้องมี Wi-Fi หรือเปลี่ยนฮาร์ดแวร์**
 
- อุปกรณ์รุ่นเก่า เช่น PLC, มิเตอร์ไฟฟ้า, เครื่องมือวัดในโรงงาน หรือไมโครคอนโทรลเลอร์ที่ไม่มีโมดูลเครือข่าย มักสื่อสารได้เพียง Serial (UART, RS-232, RS-485) อุปกรณ์เหล่านี้เพียงส่งข้อความบรรทัดเดียวอย่าง `{"voltage":1.65,"raw":2048}` ออกทางสายเหมือนเดิม
- `SerialBridgeWorker` อ่านข้อมูลนั้น แล้วเผยแพร่ไปยัง Topic มาตรฐาน `iot/esp32/telemetry` และเก็บค่าล่าสุดไว้ให้ `/api/telemetry/latest` ทำให้แอป Flutter แดชบอร์ด หรือระบบคลาวด์ใดๆ ที่รองรับ MQTT หรือ HTTP ใช้ข้อมูลได้ทันที โดยไม่ต้องรู้ว่าต้นทางเป็นสาย Serial
- การสื่อสารเป็นแบบสองทาง คำสั่งจาก REST API (`POST /api/led/on`) ถูกแปลงเป็นคำสั่ง Serial `LED:ON` ส่งกลับไปควบคุมอุปกรณ์ได้ อุปกรณ์รุ่นเก่าจึงถูกสั่งงานจากระยะไกลได้ด้วย
- งานที่ซับซ้อน เช่น การเชื่อมต่อเครือข่าย การเข้ารหัส TLS การยืนยันตัวตน และการเชื่อมต่อคลาวด์ ทำที่ Gateway เพียงจุดเดียว ไม่ต้องแก้เฟิร์มแวร์ของอุปกรณ์เดิม และประหยัดกว่าการเปลี่ยนอุปกรณ์ใหม่ทั้งหมด
```

2. เพราะเหตุใดเราจึงต้องใช้ `BackgroundService` ในการอ่านข้อมูล Serial แทนที่จะเปิดพอร์ตอ่านตรงๆ ภายในฟังก์ชันของ REST API?

```text
**เพราะข้อมูล Serial ไหลเข้ามาต่อเนื่องตลอดเวลา จึงต้องมีตัวอ่านที่ทำงานตลอดเวลาเพียงตัวเดียว ส่วน REST API ทำงานเฉพาะเมื่อมีคำขอเข้ามาเท่านั้น**
 
- **ข้อมูลไม่สูญหายและเป็นปัจจุบัน** ESP32 ส่งข้อมูลทุกประมาณ 500 มิลลิวินาที หากอ่านเฉพาะตอนมีคำขอ REST ข้อมูลระหว่างคำขอจะค้างในบัฟเฟอร์ แล้วถูกอ่านออกมาเป็นค่าเก่า หรือบัฟเฟอร์เต็มจนข้อมูลหาย ส่วน `BackgroundService` อ่านต่อเนื่อง ทำให้ `GatewayStateStore` มีค่าล่าสุดเสมอ และส่งต่อเข้า MQTT ได้ทันทีแม้ไม่มีใครเรียก API
- **พอร์ต COM เปิดได้ทีละโปรแกรม** บน Windows พอร์ต COM เปิดได้แบบ Exclusive Access หากแต่ละคำขอ REST เปิดพอร์ตเอง คำขอที่เข้ามาพร้อมกันจะเปิดพอร์ตไม่สำเร็จ การให้ Worker เป็นเจ้าของพอร์ตเพียงตัวเดียว แล้วให้ API เรียกผ่าน `SendSerialCommand()` จึงไม่เกิดการแย่งพอร์ต
- **API ตอบสนองเร็ว** การอ่าน Serial ต้องรอข้อมูล (`ReadTimeout = 1000` มิลลิวินาที) หากทำในฟังก์ชัน API ทุกคำขอต้องรอจนได้ข้อมูลหรือหมดเวลา เมื่อแยกออกมา API เพียงอ่านค่าจากหน่วยความจำ จึงตอบกลับได้ทันที
- **จัดการวงจรชีวิตอัตโนมัติ** `BackgroundService` เริ่มทำงานพร้อม Kestrel และได้รับ `CancellationToken` เพื่อหยุดและปิดพอร์ตอย่างถูกต้องเมื่อปิดโปรแกรม รวมถึงมีลูปพยายามเปิดพอร์ตใหม่ทุก 3 วินาทีเมื่อถอดสายแล้วเสียบกลับมา
```
