# ใบงานการทดลองที่ 13.1
## 4. คำถามท้ายการทดลอง (Review Questions)
1. การรัน Embedded MQTT Broker ภายใน Kestrel มีข้อได้เปรียบกว่าการติดตั้งซอฟต์แวร์ Mosquitto แยกต่างหากอย่างไรในแง่ของการกระจายงาน (Deployment) และการประมวลผลข้อมูลในหน่วยความจำ?

```text
**Broker, REST API และตรรกะการประมวลผลรวมอยู่ในโปรแกรมเดียว จึงติดตั้งง่ายกว่า และประมวลผลข้อความได้ทันทีในหน่วยความจำโดยไม่ต้องส่งต่อผ่านเครือข่าย**
 
- **Deployment แบบไฟล์เดียว** ใช้ `dotnet publish` ได้โปรแกรมเดียวที่มีทั้ง HTTP พอร์ต 5000 และ MQTT พอร์ต 1883 ไม่ต้องติดตั้ง Mosquitto แยก ไม่ต้องดูแล `mosquitto.conf` และไม่เกิดปัญหา Broker ทำงานซ้อนกันกับ Windows Service เหมือนที่พบในแล็บ 11.2 อีกทั้งนำไปรันบน Windows, Linux หรือบรรจุเป็น Docker Image เดียวได้
- **การตั้งค่าและดูแลรวมศูนย์** Broker ใช้ระบบ Configuration, Logging และ Dependency Injection เดียวกับ ASP.NET Core ทำให้เริ่ม หยุด อัปเดต และตรวจสอบระบบได้ในจุดเดียว
- **ประมวลผลในหน่วยความจำโดยตรง** ข้อความที่เข้ามาอยู่ในรูป Object ภายในโปรเซสเดียวกันทันที เช่น `args.ApplicationMessage` ใน `InterceptingPublishAsync` หากใช้ Mosquitto แยก ต้องเขียนโปรแกรม Client อีกตัวมา Subscribe ข้อความผ่านเครือข่ายก่อนนำไปประมวลผล ซึ่งเพิ่มความหน่วงและจุดที่อาจล้มเหลว
- **เชื่อมโยงกับ REST และบริการอื่นได้ทันที** ค่าล่าสุดของเซนเซอร์ที่เก็บไว้ในหน่วยความจำ สามารถส่งกลับผ่าน REST Endpoint, บันทึกลงฐานข้อมูล หรือส่งต่อไปยังเว็บแดชบอร์ดได้โดยตรง เหมาะกับบทบาท Edge Gateway ที่รวมหลายโปรโตคอลไว้ในเครื่องเดียว
```

2. ฟังก์ชัน `InterceptingPublishAsync` ใน MQTTnet สามารถนำไปประยุกต์ใช้ในการกรองข้อมูลที่ผิดปกติ (Edge Validation) ก่อนส่งต่อให้ Client อื่นได้อย่างไร?

```text
**`InterceptingPublishAsync` ทำงานก่อนที่ Broker จะส่งข้อความต่อให้ Subscriber จึงตรวจสอบ แก้ไข หรือปฏิเสธข้อความได้ตั้งแต่ปลายทางขาเข้า**
 
- **ปฏิเสธข้อความที่ไม่ถูกต้อง** ตรวจ Payload ว่าเป็น JSON ที่ถูกต้องและค่าอยู่ในช่วงที่เป็นไปได้ เช่น แรงดันต้องอยู่ระหว่าง 0–3.3 V หากผิดปกติให้ตั้ง `args.ProcessPublish = false` ข้อความจะไม่ถูกส่งต่อให้ Client อื่นและไม่ถูกเก็บเป็น Retained Message
- **ควบคุมสิทธิ์ตาม Client** ใช้ `args.ClientId` ตรวจว่า Client นั้นได้รับอนุญาตให้ส่งไปยัง Topic นั้นหรือไม่ เช่น เฉพาะบอร์ด ESP32 เท่านั้นที่ส่งไปยัง `iot/esp32/telemetry` ได้ ป้องกันการส่งข้อมูลปลอม
- **ปรับแต่งข้อมูลก่อนส่งต่อ (Enrichment)** แก้ไข `args.ApplicationMessage` ได้ เช่น ปัดเศษทศนิยม เติม Timestamp ของ Gateway หรือแปลงหน่วย ทำให้ Client ปลายทางได้รับข้อมูลรูปแบบเดียวกันเสมอ
- **ตรวจจับเหตุการณ์ผิดปกติ** บันทึก Log ข้อความที่ถูกปฏิเสธ นับจำนวนข้อความต่อ Client เพื่อจำกัดอัตราการส่ง (Rate Limiting) หรือส่งแจ้งเตือนเมื่อค่าเกินเกณฑ์
```
