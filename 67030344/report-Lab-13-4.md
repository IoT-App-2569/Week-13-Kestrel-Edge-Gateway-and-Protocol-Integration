# ใบงานการทดลองที่ 13.4 (The Grand Finale)
## 4. บทสรุปและคำถามส่งท้ายภาคการศึกษา (Capstone Retrospective)

1. ตลอดระยะเวลา 13 สัปดาห์ การเดินทางจากระดับบิตและรีจิสเตอร์ของเซนเซอร์ สู่เฟรมเวิร์ก FreeRTOS, ผ่านโปรโตคอลเครือข่ายท้องถิ่น, สู่ระบบคลาวด์ MQTT, หน้าจอมือถือ Flutter, และมาบรรจบที่ Kestrel Edge Gateway... สถาปัตยกรรมชิ้นใดที่ท่านคิดว่ามีความท้าทายเชิงวิศวกรรมมากที่สุด? เพราะเหตุใด?

```text
**Kestrel Edge Gateway มีความท้าทายมากที่สุด เพราะต้องทำให้ 4 โปรโตคอลที่ทำงานต่างกันโดยสิ้นเชิง มีสถานะของระบบตรงกันตลอดเวลา**
 
- **คำสั่งเข้ามาได้จากหลายทาง แต่ไปถึงอุปกรณ์ได้ทางเดียว** คำสั่งเปิด-ปิดไฟมาได้ทั้งจากแอป Flutter (MQTT), หน้าเว็บ (SignalR) และระบบภายนอก (REST) แต่ทั้งหมดต้องรวมไปที่พอร์ต Serial เดียวซึ่งเปิดได้ทีละโปรแกรม และเมื่อสถานะเปลี่ยน ต้องกระจายกลับไปให้ทุกช่องทางรับรู้ ไม่ว่าคำสั่งจะมาจากทางใด
- **ต้องเลียนแบบพฤติกรรมของอุปกรณ์ MQTT แทนบอร์ด** แอป Flutter จากสัปดาห์ที่ 12 รอข้อความ `online` ที่ `iot/esp32/status` และรอ ACK ที่ `iot/esp32/led_ack` แต่ ESP32 ในสัปดาห์นี้สื่อสารผ่านสาย Serial และไม่รู้จัก MQTT เลย Gateway จึงต้องสร้างข้อความเหล่านี้แทนบอร์ด รวมถึงแปลงเหตุการณ์สายหลุดเป็นสถานะ `offline` ทดแทนกลไก LWT
- **การทำงานพร้อมกันหลายเธรด** การอ่าน Serial ใน `BackgroundService` การรับข้อความใน MQTT Broker และการรับคำขอ REST และ SignalR เกิดขึ้นพร้อมกันบนคนละเธรด ข้อมูลที่ใช้ร่วมกัน เช่น สถานะไฟและตัวนับสถิติ ต้องป้องกันการแย่งกันเขียน
- **ปัญหาที่หาสาเหตุได้ยาก** เมื่อระบบไม่ทำงาน สาเหตุอาจอยู่ที่ชั้นใดก็ได้ ตั้งแต่สาย USB พอร์ต COM ที่ถูกโปรแกรมอื่นล็อกไว้ Firewall ที่บล็อกพอร์ต 1883 ไปจนถึงชื่อ Topic ที่ไม่ตรงกันระหว่างแอปกับ Gateway ต้องเข้าใจทุกชั้นของระบบจึงจะแก้ไขได้

```

2. หากท่านต้องนำระบบนี้ไปติดตั้งในโรงงานอุตสาหกรรมจริง สิ่งใดคือ 3 ปัจจัยแรกที่ต้องดำเนินการเพิ่มเติมเพื่อความปลอดภัยและความมั่นคงระดับองค์กร?

```text
**ต้องปรับปรุงความปลอดภัยของการสื่อสาร ความทนทานของระบบ และความสามารถในการเฝ้าระวังและตรวจสอบย้อนหลัง**
 
1. **ความปลอดภัยของการสื่อสารและการยืนยันตัวตน (Security)** ปัจจุบันทุกช่องทางเปิดโดยไม่มีการยืนยันตัวตน ใครที่อยู่ในเครือข่ายเดียวกันก็เปิด-ปิดอุปกรณ์ได้ ต้องเปลี่ยนเป็น MQTTS พอร์ต 8883 พร้อม mTLS สำหรับอุปกรณ์เหมือนแล็บ 11.3 ใช้ HTTPS กับ REST และ SignalR พร้อมการยืนยันตัวตนด้วย Token กำหนด ACL ให้แต่ละผู้ใช้และอุปกรณ์เข้าถึงเฉพาะ Topic ที่ได้รับอนุญาต และแยกเครือข่ายเครื่องจักร (OT) ออกจากเครือข่ายสำนักงาน (IT) ด้วย VLAN และ Firewall
2. **ความทนทานและความพร้อมใช้งาน (Reliability)** Gateway เป็นจุดล้มเหลวจุดเดียว ต้องติดตั้งเป็น Windows Service หรือ systemd ที่เริ่มทำงานใหม่อัตโนมัติเมื่อแครช พิจารณา Gateway สำรอง และจ่ายไฟผ่าน UPS เพิ่มระบบเก็บข้อมูลชั่วคราวลงฐานข้อมูลเมื่อปลายทางไม่พร้อม (Store and Forward) เพื่อไม่ให้ข้อมูลการผลิตสูญหาย และเปลี่ยนจากสาย USB เป็นมาตรฐานอุตสาหกรรมอย่าง RS-485 หรือ Modbus ที่ทนสัญญาณรบกวนและลากสายได้ไกลกว่า
3. **การเฝ้าระวังและตรวจสอบย้อนหลัง (Observability & Audit)** บันทึก Log ทุกคำสั่งควบคุม ว่าใครสั่ง สั่งจากช่องทางใด และเวลาใด เพื่อตรวจสอบย้อนหลังเมื่อเกิดเหตุ ส่งตัวชี้วัดของระบบเข้าเครื่องมือเฝ้าระวังอย่าง Prometheus หรือ Grafana พร้อมตั้งการแจ้งเตือนเมื่ออุปกรณ์หลุดหรืออัตราข้อมูลผิดปกติ และมีกระบวนการอัปเดตเฟิร์มแวร์และซอฟต์แวร์ที่ปลอดภัยและย้อนกลับได้
```

3. ขอแสดงความยินดีกับนักศึกษาทุกท่านที่สำเร็จการฝึกอบรมการพัฒนาแอปพลิเคชันไอโอทีระดับมืออาชีพอย่างสมบูรณ์แบบ! 🎉
