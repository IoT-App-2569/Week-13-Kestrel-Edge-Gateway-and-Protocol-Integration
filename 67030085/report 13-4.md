1. สามารถประกอบและเชื่อมโยงระบบไอโอทีที่ใช้ 4 โปรโตคอล (Serial, MQTT, REST, WebSockets) ให้ทำงานสอดประสานกันได้สมบูรณ์
2. สามารถทดสอบการซิงโครไนซ์สถานะแบบสามประสาน (Hardware <-> Mobile App <-> Web Dashboard) แบบเรียลไทม์ได้
3. สามารถพิสูจน์คุณสมบัติความอยู่รอดในระดับขอบ (Local Survivability) เมื่อตัดการเชื่อมต่ออินเทอร์เน็ตภายนอกได้
4. สามารถวัดความหน่วงเวลาเปรียบเทียบในแต่ละเส้นทางการสื่อสารของระบบได้

### กิจกรรมที่ 13-4.1: การเตรียมพร้อมทุกระบบ

   * ตรวจสอบว่า `Program.cs` รวมบริการทั้ง Embedded MQTT Broker, Serial Bridge, REST APIs, และ SignalR ไว้ครบถ้วน

### กิจกรรมที่ 13-4.3: การทดสอบความทนทานในสภาวะตัดเน็ต (Local Survivability Challenge)

1. ทำการ **ถอดสาย LAN หรือปิดการเชื่อมต่ออินเทอร์เน็ตภายนอก** ของเครื่องคอมพิวเตอร์และมือถือ (คงไว้เฉพาะเครือข่าย Wi-Fi วงแลนท้องถิ่นที่ไม่มีเน็ต)
2. สังเกตการทำงาน:
   * บอร์ด ESP32 ยังคงส่งข้อมูลได้หรือไม่?
   * แอปมือถือ Flutter และเว็บแดชบอร์ดยังสามารถเปิดดูค่าและสั่งงานหลอดไฟได้หรือไม่?
3. **สรุปผล**: ระบบที่ออกแบบด้วยสถาปัตยกรรม **Converged Edge Gateway** มีความสามารถในการอยู่รอด (Survivability) อย่างสมบูรณ์แบบ 100% โดยไม่ล่มสลายตามสัญญาณอินเทอร์เน็ตภายนอก

## 4. บทสรุปและคำถามส่งท้ายภาคการศึกษา (Capstone Retrospective)

1. ตลอดระยะเวลา 13 สัปดาห์ การเดินทางจากระดับบิตและรีจิสเตอร์ของเซนเซอร์ สู่เฟรมเวิร์ก FreeRTOS, ผ่านโปรโตคอลเครือข่ายท้องถิ่น, สู่ระบบคลาวด์ MQTT, หน้าจอมือถือ Flutter, และมาบรรจบที่ Kestrel Edge Gateway... สถาปัตยกรรมชิ้นใดที่ท่านคิดว่ามีความท้าทายเชิงวิศวกรรมมากที่สุด? เพราะเหตุใด?
   * **สถาปัตยกรรมที่มีความท้าทายมากที่สุดคือ:** **"All-in-One Multi-Protocol Converged Edge Gateway (สัปดาห์ที่ 13)"**
   * **เหตุผลเชิงวิศวกรรม:**
     * **1. การบริหารจัดการความหลากหลายของโปรโตคอล (Protocol Heterogeneity & Synchronization):** เป็นจุดที่ต้องเชื่อมโยงระบบ 4 ขั้วที่มีธรรมชาติการทำงานแตกต่างกันโดยสิ้นเชิง ได้แก่ ฮาร์ดแวร์อนุกรม (Serial Byte Stream แบบมี Exclusive Lock), ระบบส่งข้อความ Asynchronous Pub/Sub (MQTTnet), การตอบสนองตามคำขอแบบ Stateless (HTTP REST API), และการสตรีมมิ่งสดสองทางแบบ State-full (SignalR WebSockets) เข้าสู่ Process เดียวกัน
     * **2. การออกแบบการจัดการข้อมูลและ Concurrency แบบ Thread-Safe:** ต้องจัดการ Background Task (`BackgroundService`) เพื่ออ่านสตรีม Serial อย่างต่อเนื่องโดยไม่เกิด Block I/O พร้อมทั้งอัปเดต State กลางแบบ Zero-lock/Thread-Safe (`GatewayStateStore`) และกระจายข้อมูลแบบ Real-time ไปยังทุกโปรโตคอลย่อยพร้อมกันในระดับ Microsecond
     * **3. การรักษาความต่อเนื่องในการทำงาน (Fault Isolation & Local Survivability):** เกตเวย์ต้องมีความทนทานสูง หากมีโปรโตคอลใดสะดุดหรือหลุดการเชื่อมต่อ (เช่น สาย Serial หลวม หรือเน็ตหลุด) ระบบส่วนอื่นต้องไม่แครชตาม และยังสามารถทำงานในระดับขอบได้อย่างสมบูรณ์ 100% โดยไม่ต้องพึ่งพาคลาวด์

2. หากท่านต้องนำระบบนี้ไปติดตั้งในโรงงานอุตสาหกรรมจริง สิ่งใดคือ 3 ปัจจัยแรกที่ต้องดำเนินการเพิ่มเติมเพื่อความปลอดภัยและความมั่นคงระดับองค์กร?
   * **1. การเข้ารหัสและพิสูจน์ตัวตนแบบสองทางระดับองค์กร (Mutual TLS / mTLS & Transport Security):**
     * ยกระดับการสื่อสารทุกช่องทางให้เข้ารหัสอย่างสมบูรณ์ เปลี่ยน MQTT เป็น MQTTS (พอร์ต 8883) และเปิดใช้ HTTPS/WSS (พอร์ต 5001/443)
     * บังคับใช้ใบรับรองดิจิทัลแบบ **mTLS (Mutual TLS)** ยืนยันตัวตนสองทางระหว่าง Edge Gateway และอุปกรณ์โหนดเซนเซอร์ เพื่อป้องกันการปลอมแปลงฮาร์ดแวร์ (Device Spoofing) และการดักฟังข้อมูล (Man-in-the-Middle Attack) ในเครือข่ายโรงงาน
   * **2. การกำหนดสิทธิ์แบบละเอียดและการรักษาความปลอดภัยระดับ API (Granular RBAC, API Key & Rate Limiting):**
     * จัดการสิทธิ์การเข้าถึงตามบทบาท (Role-Based Access Control) เช่น อนุญาตให้แอป Dashboard อ่านค่าได้อย่างเดียว ส่วนสิทธิ์การสั่งงาน Actuator (ควบคุมหลอดไฟ/รีเลย์) ต้องผ่านการยืนยัน API Key หรือ JWT Token
     * มีการจำกัดความถี่ในการเรียกใช้งาน (Rate Limiting Middleware) และตรวจสอบความถูกต้องของข้อมูล (Edge Validation) ผ่าน `InterceptingPublishAsync` เพื่อป้องกันการโจมตีแบบ DoS/Spamming
   * **3. กลไกความทนทานและการสำรองข้อมูลออฟไลน์ (Store-and-Forward & Hardware Failover):**
     * พัฒนาระบบ **Store-and-Forward** โดยใช้ Local Database (เช่น SQLite / RocksDB) เก็บบัฟเฟอร์ข้อมูล Telemetry ไว้บนเกตเวย์เมื่อระบบอินเทอร์เน็ตโรงงานหรือลิงก์ส่งต่อไปยัง Data Center ขาดหาย และทำการซิงก์ข้อมูลย้อนหลังอัตโนมัติเมื่อเครือข่ายกลับมาปกติ
     * ติดตั้งระบบ **Watchdog Timer** และทำ Redundancy (Dual Gateway High-Availability) เพื่อให้ระบบควบคุมกระบวนการผลิตทำงานได้ต่อเนื่อง 24/7 ไม่มีภาวะ Single Point of Failure

3. ขอแสดงความยินดีกับนักศึกษาทุกท่านที่สำเร็จการฝึกอบรมการพัฒนาแอปพลิเคชันไอโอทีระดับมืออาชีพอย่างสมบูรณ์แบบ! 🎉
