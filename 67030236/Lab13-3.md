## 4. คำถามท้ายการทดลอง
1. เพราะเหตุใด SignalR จึงให้ประสบการณ์การใช้งาน (UX) บนหน้าเว็บที่ดีกว่าการใช้คำสั่ง JavaScript `setInterval()` เพื่อทำ HTTP GET Polling ซ้ำๆ ทุก 500 ms?
```
เรียลไทม์แท้จริง (No Delay): เซิร์ฟเวอร์ดันข้อมูลหาหน้าเว็บทันทีเมื่อมีค่าใหม่ ไม่ต้องรอรอบเวลา 500 ms

หน้าจอลื่นไหล ไม่กระตุก: ไม่ต้องเปิด-ปิด HTTP request ซ้ำๆ ลดภาระ CPU และแรมของเบราว์เซอร์

ข้อมูลไม่ตีกัน (No Race Condition): ข้อความมาตามลำดับ ป้องกันปัญหาผลลัพธ์ request ช้า-เร็วสลับกันจนหน้าจอกระพริบย้อนสถานะ

ไม่เปลืองเน็ต: ส่งเฉพาะตัวข้อมูลเพียวๆ ผ่าน WebSocket ท่อเดียว ไม่ต้องพ่วง HTTP Header ก้อนใหญ่ซ้ำทุกครึ่งวินาที
```
2. การคำนวณและแสดงผล Protocol Convergence Metrics ส่งผลดีต่อการตรวจสอบสุขภาพของระบบเครือข่ายไอโอทีในระดับโรงงานอย่างไร?
```
ตรวจจับจุดเสี่ยงล่วงหน้า (Predictive Maintenance): รู้ว่าลิงก์หรืออุปกรณ์ตัวไหนเริ่มส่งสัญญาณช้าผิดปกติหรือสูญเสียแพ็กเก็ต ก่อนที่ระบบสื่อสารในไลน์ผลิตจะตัดการเชื่อมต่อจริง

แยกแยะสาเหตุของปัญหาได้ทันที (Fast Root-Cause Analysis): ชี้ชัดได้ว่าความล่าช้าเกิดจากสัญญาณรบกวนในสาย (Physical/Serial), การรอคิวของ Gateway หรือคอขวดบนเน็ตเวิร์ก (MQTT Broker/Kestrel)

การันตีความปลอดภัยและ SLA: ติดตามว่าเวลาตอบสนอง (Latency) และการกู้คืนเครือข่าย (Convergence Time) ยังอยู่ในเกณฑ์ Deterministic ตามข้อกำหนดของเครื่องจักรหรือไม่ ป้องกันการสูญเสียข้อมูลสำคัญในกระบวนการผลิต
```
