> [!WARNING] **ข้อพึงระวังเรื่องพอร์ตสื่อสารอนุกรม (Serial Port Exclusive Lock):**
> 1. ตรวจสอบหมายเลข COM Port ของบอร์ด ESP32 ผ่าน Device Manager แล้วแก้ไขตัวแปร `_portName` ในไฟล์ `Services.cs` ให้ตรงกับเครื่องของคุณ (เช่น `COM24`)
> 2. **ต้องปิด `idf monitor`, PuTTY หรือ Serial Monitor อื่นๆ ก่อนรัน Kestrel เสมอ** เพราะบน Windows พอร์ต COM จะถูกล็อกใช้งานแบบ Exclusive Access (เปิดได้เพียง 1 โปรแกรมในเวลาเดียวกัน) หากมีโปรแกรมอื่นเปิดพอร์ตค้างไว้ C# จะเปิดพอร์ตไม่สำเร็จและส่งคำสั่งไม่ได้ (`sentToSerial: false`)

1. เสียบบอร์ด ESP32 เข้ากับเครื่อง และสั่งรัน Kestrel:
```powershell
dotnet run
```
2. ทดสอบเรียกดูค่าเซนเซอร์ผ่านเบราว์เซอร์หรือ cURL:
```powershell
curl http://localhost:5000/api/telemetry/latest
```
*สังเกตว่าจะได้ข้อมูล JSON ของแรงดันไฟฟ้าทันที!*
3. เปิด `mosquitto_sub`:
```powershell
mosquitto_sub -h 127.0.0.1 -p 1883 -t "iot/esp32/telemetry" -i "sub_client" -v
```
*สังเกตว่าข้อมูลที่อ่านจากสาย USB Serial ถูกส่งต่อเข้าหัวข้อ MQTT อัตโนมัติ!*
4. ทดสอบสั่งเปิด-ปิดไฟผ่าน REST API:
```powershell
curl -X POST http://localhost:5000/api/led/on
```
*สังเกตว่าคำสั่ง `LED:ON` ถูกส่งผ่านสาย USB เข้าไปควบคุมบอร์ดทันที!*

## 4. คำถามท้ายการทดลอง
1. สถาปัตยกรรมแบบ Serial-to-MQTT Bridge นี้ช่วยให้อุปกรณ์รุ่นเก่า (Legacy Hardware) ที่ไม่มี Wi-Fi สามารถเข้าร่วมระบบนิเวศ IoT สมัยใหม่ได้อย่างไร?
```
1. แปลง Physical Layer และ Protocol (Interface Abstraction)
การเชื่อมต่อฝั่ง Legacy: รับ-ส่งข้อมูลผ่านพอร์ตดั้งเดิม เช่น UART, RS-232, RS-485 (Modbus RTU) หรือ CAN bus

การเชื่อมต่อฝั่ง Modern: ต่อเชื่อมเข้ากับเครือข่าย IP ผ่าน Wi-Fi, Ethernet หรือ Cellular แล้วห่อหุ้มข้อมูล (Encapsulate) ส่งขึ้นเน็ตเวิร์กด้วยโปรโตคอล MQTT ผ่าน TCP/IP

2. แปลงโครงสร้างข้อมูล (Data Serialization & Normalization)
อ่าน Raw Bytes, Hex Frames หรือ Register Addresses จากสาย Serial

ทำการแปลง (Parse/Map) ให้อยู่ในรูปแบบมาตรฐาน เช่น JSON หรือ Key-Value

กำหนด Topic ตามลำดับชั้น (Topic Hierarchy) เช่น factory/line1/machine05/telemetry ทำให้ระบบปลายทาง (Cloud/Dashboard) นำไปใช้งานได้ทันทีโดยไม่ต้องเขียน Parser สำหรับฮาร์ดแวร์เฉพาะทางนั้นซ้ำอีก

3. เปลี่ยนสถาปัตยกรรมจาก Polling เป็น Pub/Sub
อุปกรณ์ดั้งเดิม: มักใช้ระบบ Master-Slave Polling (ต้องมีตัวคอยยิงคำถามซ้ำๆ เพื่อขอข้อมูล) หรือส่งข้อมูลสตรีมออกทาง Serial ตลอดเวลา

เมื่อผ่าน Bridge: Bridge จะคอยดึง/อ่านข้อมูล Serial แล้วเปลี่ยนเป็นการกระจายข่าวแบบ Publish/Subscribe

ระบบปลายทางหลายระบบ (เช่น Database, Dashboard, Alert System) สามารถ Subscribe รับข้อมูลชุดเดียวกันพร้อมกันได้ทันทีโดยไม่แย่งพอร์ต Serial กัน

4. ยกระดับความปลอดภัย (Security Layer Overlay)
Legacy Hardware ส่วนใหญ่ไม่มีระบบความปลอดภัยระดับเน็ตเวิร์ก

Bridge จะทำหน้าที่เป็นชั้นป้องกัน (Security Boundary) ให้ โดยจัดการเรื่อง:

การเข้ารหัสลับข้อมูลผ่าน TLS/SSL (MQTTS)

การยืนยันตัวตนด้วย Client Certificate หรือ Username/Password Tokens ป้องกันไม่ให้อุปกรณ์รุ่นเก่าสัมผัสกับเครือข่ายภายนอกโดยตรง

5. อัปเกรดโดยไม่ต้องแก้ไขเครื่องจักรเดิม (Zero Retrofit Impact)
ไม่จำเป็นต้องรื้อเขียน Firmware ใหม่ หรือเปลี่ยนบอร์ดควบคุมหลักของเครื่องจักรเดิม (ซึ่งมักมีค่าใช้จ่ายสูงและเสี่ยงระบบหยุดชะงัก)

เพียงแค่ต่อสาย Serial Rx/Tx จากอุปกรณ์เข้ากับบอร์ด Bridge (เช่น ESP32, Raspberry Pi หรือ Industrial IoT Gateway) เครื่องจักรเดิมก็พร้อมเชื่อมต่อคลาวด์ได้ทันที
```
2. เพราะเหตุใดเราจึงต้องใช้ `BackgroundService` ในการอ่านข้อมูล Serial แทนที่จะเปิดพอร์ตอ่านตรงๆ ภายในฟังก์ชันของ REST API?
```
1. พอร์ต Serial เป็น "Exclusive Resource" (เปิดซ้อนไม่ได้)
REST API: ตัว Request เป็นแบบ Stateless และ Concurrent หากเปิดพอร์ตในฟังก์ชัน API เมื่อมีผู้ใช้เรียกพร้อมกัน 2 คนขึ้นไป Request ที่สองจะพังทันทีด้วยข้อผิดพลาด UnauthorizedAccessException (พอร์ตถูกยึดใช้งานอยู่)

BackgroundService: ทำงานเป็น Singleton ที่เปิดพอร์ตเชื่อมต่อไว้เพียงจุดเดียวตลอดอายุของแอปพลิเคชัน

2. ป้องกันข้อมูลสูญหาย (Hardware Buffer Overflow)
การอ่านข้อมูลจาก Serial ต้องคอยดึงข้อมูลออกจาก Buffer อย่างต่อเนื่องแบบ Real-time

หากรอให้มี HTTP Request เข้ามาก่อนจึงค่อยสั่งอ่าน:

ถ้าไม่มี Request เข้ามา บัฟเฟอร์ของชิป Serial/OS จะเต็มจนเกิด Buffer Overrun และข้อมูลหาย

ข้อมูลที่อ่านได้จะเป็นข้อมูลเก่าที่ค้างอยู่ในคิว ไม่ใช่สถานะปัจจุบันของฮาร์ดแวร์

3. Connection Overhead และ Latency สูงมาก
การสั่ง SerialPort.Open() และปิดพอร์ตในทุก HTTP Request ต้องผ่าน OS System Call และการรีเซ็ตสัญญาณ DTR/RTS ซึ่งกินเวลาหลักสิบถึงร้อยมิลลิวินาที (ms) ทำให้ API ตอบสนองช้ามากโดยไม่จำเป็น

4. รูปแบบ Stream ต่อเนื่อง ขัดกับโมเดล Request-Response
ข้อมูล Serial มักสตรีมเข้ามาเรื่อยๆ โดยที่เรากำหนดเวลาเป๊ะๆ ไม่ได้

แนวทางที่ถูกต้อง: ให้ BackgroundService วนลูปอ่านข้อมูลอยู่เบื้องหลัง แล้วนำไปอัปเดตลงตัวแปรใน RAM (In-Memory Cache) หรือส่งเข้า Message Queue จากนั้นให้ฟังก์ชัน REST API ดึงค่าล่าสุดจาก RAM ไปตอบกลับ Client ได้ทันทีโดยใช้เวลาเพียงหลักเสี้ยววินาที
```
